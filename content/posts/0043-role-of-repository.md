## はじめに

先日の面接で、ある質問をされました。

> 「このアプリでは、なぜリポジトリを作っていないのですか？」

その質問を聞いた瞬間、少し詰まってしまいました。

もちろん、Repositoryパターン自体は普段から利用しています。
Androidアプリ開発では、Clean Architectureの文脈でRepositoryを導入することも多く、RoomやRetrofitなどのデータアクセス層を隠蔽する役割として理解していました。

しかし、その場では、

「なぜRepositoryが必要なのか？」
「Repositoryがない設計は悪いのか？」
「どのような場合にRepositoryを作るべきなのか？」

という本質的な部分を、うまく言語化することができませんでした。

そこで改めて、Repositoryの役割について整理してみました。

---

## Repositoryとは何か

Repositoryとは、一言で表すと、

> **アプリケーションが必要とするデータを、どこから取得・保存するかという詳細を隠蔽する層**

です。

例えば、ユーザー情報を取得する処理を考えます。

Repositoryがない場合、UseCaseやViewModelから直接データソースを呼び出すことになります。

```kotlin
class UserViewModel(
    private val dao: UserDao,
    private val api: UserApi
) : ViewModel()
```

この場合、UseCaseやViewModelは以下のようなことを知る必要があります。

* データがRoomに保存されているのか
* ネットワークAPIから取得するのか
* キャッシュを利用するのか
* オフライン時はどうするのか
* 取得失敗時にどう扱うのか

つまり、画面の責務ではない「データ取得の詳細」が流入してしまいます。

---

## Repositoryが提供するもの

Repositoryを導入すると、利用側はデータの取得元を意識する必要がなくなります。

```kotlin
interface UserRepository {
    suspend fun getUser(id: String): User
}
```

ViewModelやUseCaseは、

「ユーザー情報が欲しい」

という要求だけをRepositoryに伝えます。

その裏側では、

* Roomから取得する
* APIから取得する
* キャッシュを確認する
* 複数のデータソースを組み合わせる

といった処理をRepositoryが担当します。

つまりRepositoryは、

> **データを保存する場所ではなく、データにアクセスするための窓口**

です。

---

## なぜ今回のアプリではRepositoryを作らなかったのか

面接で質問された「守るくん」アプリでは、Repositoryを導入していません。

理由は、Repositoryによって隠蔽するべき複雑性が存在しなかったためです。

このアプリでは、設定値の保存にDataStoreを利用しています。

例えば、

* 緊急連絡先
* 最終充電日時
* 設定状態

などを保存しています。

しかし、データ取得の流れは非常に単純です。

```
DataStore
    ↓
UseCase
    ↓
Worker
```

という構造で、

「現在保存されている設定値を取得する」

という処理しかありません。

ここにRepositoryを追加すると、

```
DataStore
    ↓
Repository
    ↓
UseCase
    ↓
Worker
```

となります。

しかし、このRepositoryには、

```kotlin
class SettingRepository {
    suspend fun getPhoneNumber(): String
}
```

のようなDataStoreへの単純な委譲処理しか存在しないでしょう。

この場合、Repositoryを追加しても、

* データ取得元を隠蔽できるメリットがない
* テスト対象が増える
* クラス数が増える
* 変更点が増える

というデメリットのほうが大きくなります。

---

## Repositoryは必ず作るものではない

Repositoryの本来の目的は、

> **将来的な変更や複雑なデータ取得処理を吸収すること**

だと思います。（ただし、プロジェクトによって、役割のとらえ方は様々だとは思います。）

例えば、以下のような場合はRepositoryを導入する価値があります。

### 1. 複数のデータソースが存在する場合

例：

```
Repository
 ├─ RemoteDataSource(API)
 └─ LocalDataSource(Room)
```

APIが利用できる場合は最新データを取得し、失敗時はRoomのキャッシュを利用する、といった判断をRepositoryに閉じ込めることができます。

---

### 2. データ取得ルールが存在する場合

例えば、

* ログインユーザーの情報を取得する
* 有効期限が切れていたら更新する
* 権限によって取得するデータを変える

など、単純なCRUDでは表現できないロジックが存在する場合です。

---

### 3. データ保存方法が変わる可能性がある場合

例えば現在はDataStoreを利用していても、

将来的に、

* Roomへ変更する
* サーバー同期する
* 暗号化ストレージへ変更する

可能性がある場合、Repositoryによって変更箇所を限定できます。

---

## 面接で答えるなら

今回の質問に対しては、以下のように答えるべきでした。

> 「Repositoryはデータアクセスの詳細を隠蔽するための層だと考えています。ただ、今回のアプリではDataStoreへの単純なアクセスしかなく、Repositoryを作っても単なる委譲クラスになってしまいます。そのため、責務のない抽象化は増やさず、必要になったタイミングでRepositoryを導入する判断をしました。」

Repositoryの必要性をとくに感じなかったため、

なぜRepositoryを作らなかったのかを面接時に瞬時に答えられませんでしたが、

逆に、どんな機能を追加したらRepositoryが必要かを考えれば、瞬時に答えられたかもしれないと感じました。

---

## おわりに

今回の面接では、Repositoryを知らなかったわけではありません。

しかし、「いつ使うべきなのか」という判断基準を、その場で整理して説明することができませんでした。

設計では、よく使われるパターンを適用すること自体よりも、

* なぜその構造が必要なのか
* その構造によって何が改善されるのか
* 今の問題に対して本当に必要なのか

を考えることが重要です。

Repositoryも同じで、作ること自体が目的ではありません。

**解決したい問題があるから、そのための構造を選択する。**

今回の面接は、「その設計で、将来どんな問題が生まれそうか」を瞬時に想像する訓練になりました。
